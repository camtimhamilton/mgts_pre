# ПУЛЬС · архитектура парного анализа v2

Дашборд и ML запускаются как два процесса FastAPI. Возможность воспроизвести старую демонстрацию сохранена на `/legacy` и ML API v1. Текущий экран на `/` использует только API v2.

## От строки книги до карточки

1. Backend читает книги по исходным заголовкам. Анкета наставника или явная запись реестра связывает ID наставника и стажёра. Подразделение служит проверкой согласованности. Импорт двух книг проходит в одной транзакции. Сохраняются лист, исходные заголовки, номер и значения строки.
2. Backend хранит версии анкет в SQLite. Ключ текущей анкеты состоит из пары, месяца и роли. При получении новой версии сохраняется предыдущая. Для ссылки на источник используется идентификатор конкретной редакции `source_id`.
3. По событию формы backend обновляет реестр и анкету, инвалидирует зависимые результаты и запрашивает анализ ML. Открытый дашборд проверяет лёгкий счётчик изменений. Изменение вызывает запрос актуальной области. Каждый запрос экрана можно отменить, отображается ответ только на последний запрос.
4. ML получает нормализованные текущие редакции и реестр пар. Одна анкета преобразуется в оценки, текстовые сигналы и ссылки на источники. Результат интерпретации сохраняется в локальном SQLite с учётом входа, роли, версии, конфигурации модели и промптов.
5. Backend проверяет структуру ML-ответа, происхождение доказательств и арифметические инварианты перед сохранением. Снимок анализа и выбранная база сценария доступны отдельно от текущей фактической аналитики. Тексты, гипотезы и исходные ответы относятся к приватным данным.

## Индексы и полнота

Для пары и месяца X и Y вычисляются по независимым наборам факторов перспектив наставника и стажёра. Для каждой роли сумма максимальных весов равна 100. Степень фактора равна максимуму принятых текущих негативных сигналов, включая отображённую в шкалу 0–1 оценку. Вклад равен весу, умноженному на степень. Положительное наблюдение и повтор одного отрицательного наблюдения не изменяют вклад другого фактора.

Для неизвестной степени хранятся статус и отсутствие значения. Покрытие равно сумме весов известных факторов, делённой на 100. Для частично известной стороны доступна наблюдаемая сумма и её покрытие. При отсутствии содержательных наблюдений индекс равен `null`. При низком покрытии показывается серый цвет, отдельные выявленные вклады доступны в детализации. Вызов API позволяет указать текущий контрольный месяц.

Z = (X + Y) / 2 при пригодности обеих сторон. Для диапазона или программы K состоит из пригодных наблюдений «пара × месяц» в области. X, Y и Z усредняются с равным весом по одному K. Отдельная `side_statistics` учитывает все пригодные анкеты роли. Сырые данные сохраняют шкалу 1–5 и пропуски. Тексты, тренд, расхождения перспектив и повторяемость имеют собственные источники. Округление выполняет интерфейс.

## Условный сценарий

Каждый выбор содержит идентификатор мероприятия и область применения. Индивидуальные мероприятия могут пересекаться с совместным мероприятием. Целью служит конкретный фактор пары, месяца, роли и редакции анкеты в зафиксированной версии анализа. По объединению выбранных экземпляров ML условно исключает их исходные вклады. Затем пересчитываются месяцы и агрегаты на прежней выборке. В ответе есть отдельные потенциальное и дополнительное снижение при текущем выборе.

Фактические анкеты и индексы сохраняются. Сессионный черновик переносит выбор между областями. Именованное сохранение создаёт отдельный снимок в SQLite. Доступны события выбора, снятия, сохранения и восстановления. Сценарий зависит от области просмотра при сохранении и всех областей выбранных мероприятий. Изменение анкеты в этой области или методологии делает прежнюю базу устаревшей. Если новая анкета относится к иной паре или месяцу вне зависимостей, восстановление возвращает исходный снимок вместе с обновлённой матрицей. При конфликте человек выбирает мероприятия заново.

## Происхождение результата

Версионированная политика, веса, пороги, вопросы, критерии мероприятий и семантические правила находятся в `ml_service/knowledge_base/v2/`. По точному адресу анкеты и вопросу открывается количественный ответ или текст с подсветкой. Для каждой интерпретации различаются принятый сигнал, отклонённый сигнал и гипотеза на уточнение. Карточки формируются программно по этим данным. Технические поля включают версии, идентификатор анализа, время обработки и обновления.

Режим текстового анализа задаётся явно. `local_rules` работает без моделей. `local_encoder` дополняет правила предварительными тематическими соответствиями локальной мультиязычной нейросети. Такие соответствия показываются для ручной проверки и имеют нулевую степень. `deepseek` передаёт только точный разрешённый синтетический пример, валидирует JSON, ссылки, цитаты и решения отдельного валидатора. Ошибка компонента отражается в результате. Характеристики диапазонов, переключение карточек и сценарии используют сохранённые интерпретации.

## Контракт интеграции

Схемы и примеры запросов и ответов находятся в `integration/`. Соответствие полей интерфейсу описано в [dashboard_mapping.md](integration/dashboard_mapping.md). Предшествующая однокомпонентная спецификация сохранена для поддержки старых снимков в [архиве ML v1](ml_service/ARCHITECTURE.md).
