# Интеграция ML-сервиса из ветки `ml`

Оценка: **технически выполнимо**, 4–6 человеко-дней, три продуктовых решения до начала кода.
В критический путь финала не берём: там 3 часа и живые данные, а интеграция требует
изменения политики доступа к реальным комментариям.

Ветка: `origin/ml`, один коммит, независимая история, автор dmitryz1024.
Проверено: 131 тест проходит, сервис поднимается, `/v1/analyze` отдаёт заявленные числа.

---

## 1. Что именно интегрируем

Их сервис — только ML-слой, без приёма данных и без интерфейса. Контракт:

```
POST /v1/analyze   SurveyPeriod  → AnalysisResult (10 факторов, score, coverage, рекомендации)
POST /v1/scenario  analysis_id + action_ids → условный вычет
GET  /v1/analysis/{id} → неизменяемый снапшот
```

Вход — нормализованный пакет: `program_id`, `intern_id`, `period` 1..6, `mapping_version`,
`responses[]` с `respondent_role` и `answers[]` (`question_id`, `type`, `value`, `scale_min/max`).
Идентификаторы обезличенные. Наш backend остаётся мастер-системой и источником истории.

---

## 2. Три решения, без которых код бессмысленен

### Решение 1. Реальные данные и провайдер

Сейчас у автора fail-closed: реальный DeepSeek разрешён только для точных синтетических
входов из allowlist. На незнакомом тексте — проверено руками:

```
status: partial, score: 6.0, warnings: ['unknown_mock_fixture']
```

То есть числа считаются, а текст не анализируется. На финале будут живые комментарии МГТС.
Варианты:

| Вариант | Что нужно | Риск |
|---|---|---|
| A. Открыть их провайдера для реальных данных | правка политики автором + согласие МГТС на внешнюю модель | данные уходят в DeepSeek, нужна юридическая ясность |
| B. Свой провайдер под их схему | реализовать адаптер в их код (промпт + JSON-схема) | 1–2 дня, ломает их инварианты безопасности |
| C. Только числа | ничего, работает сегодня | нет текстового NLP — теряется главное |

Без решения 1 интеграция даёт «второе мнение по оценкам», а не полноценный анализ.

### Решение 2. Какой индекс главный

У нас: 6 факторов, риск 0–100, полосы 35/60, вклады целые и складываются.
У них: 10 факторов, score = сумма вес × выраженность, полосы 20/40, плюс coverage и priority.

Подставить их score в нашу карточку — смешать две модели. Варианты:

- **Заменить наш расчёт на их** — честнее методологически, но переделка UI, порогов,
  сценариев и всех тестов; на финале недопустимо.
- **Оставить наш индекс, их показывать отдельным блоком** «экспертная оценка R01–R10» —
  безопасно, но два числа на экране путают жюри.
- **Гибрид**: их числовой контур (rating-only) + наши текстовые сигналы, один снапшот,
  их факторы как объяснение. Компромисс, но требует явной формулы сведения.

Рекомендация: если делать — замена индекса, но после финала, с отдельной веткой и тестами.

### Решение 3. Покрытие анкеты

Их модель ждёт вопросы на 10 факторов. У нас шесть шкал. Максимальное покрытие весов
при текущей анкете — около 47% (`R01 12 + R03 10 + R04 8 + R07 7 + R09 10`), а порог
`min_coverage` у них 0.6. Значит **каждый человек всегда получит `insufficient_data`**
и не попадёт в обычное ранжирование.

Варианты: добавить 4 вопроса в анкету (R02, R05, R06, R08) — правка формы и мок-набора;
или понизить порог в их политике (тогда это уже не их методология).

## 3. План работ

| Этап | Содержание | Оценка |
|---|---|---|
| 0 | Решения 1–3, согласование с автором ветки | 0.5 дня |
| 1 | `services/ml`: subtree из `origin/ml`, Dockerfile, контейнер, healthcheck, внутренняя сеть | 0.5 дня |

| 3 | Маппинг выхода: 10 факторов → причины, `conflicting` → состояние, coverage → «мало данных», рекомендации → шаги | 1 день |
| 4 | Реальный текст по варианту A или B | 1–2 дня |
| 5 | Флаг `ML_MODE`, деградация, тесты, деплой, репетиция | 0.5–1 день |

Итого: **4–6 дней**. Для сравнения, весь текущий продукт занял примерно столько же.

## 4. Архитектура интеграции

```
Яндекс Форма → /api/ingest → наш backend (мастер-система)
                                   │
                                   ├─ наш scoring (индекс, история, сценарии)
                                   │
                                   └─ ML_MODE=sidecar → POST /v1/analyze → сервис ml
                                                             │
                                   сохранение их ответа в наш snapshot.data_json.ml
```

Правила:

- ML-сервис только во внутренней сети, без публичного порта; наружу — только наш API.
- Наш снапшот иммутабелен, их ответ кладём целиком в `data_json.ml` с версией KB и mapping.
- `ML_MODE=off` по умолчанию; при выключенном флаге поведение и тесты не меняются.
- Ошибка или таймаут ML-сервиса не ломает карточку: показываем наш расчёт и плашку.
- История и динамика остаются нашими: их сервис считает один период и не хранит историю.

## 5. Что забираем без интеграции (дёшево и полезно)

- `coverage` и статус «недостаточно данных» вместо «низкий риск» при малом числе ответов.
- `conflicting` как отдельное состояние, когда стажёр и наставник противоречат.
- R10-логика: прямое «хочу уйти» — флаг и разговор, а не баллы.
- Не ранжировать в топ при покрытии ниже порога.
- Экспертный словарь R01–R10 и ссылки на источники — для ответов жюри про обоснованность.

---

## 6. Критерии готовности

- `ML_MODE=off`: все текущие 120 тестов зелёные, поведение не изменилось.
- `ML_MODE=sidecar`: карточка получает данные из ML-сервиса, маппинг покрыт тестами.
- На реальном комментарии текст либо анализируется, либо явно помечен как необработанный.
- Нет секретов в логах, ML-порт не торчит наружу.
- Сквозной прогон «форма → дашборд» с включённым ML укладывается в 30 секунд.
