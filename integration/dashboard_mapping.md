# Контракт dashboard ↔ ML, adapter v1

Backend хранит исходные `Submission`, связывает людей, нормализует выгрузки, вызывает ML,
сохраняет полный ответ, агрегирует и отдаёт frontend. ML владеет факторами, правилами,
весами, порогами, coverage, индексом, рекомендациями, расхождениями и scenario.
Frontend показывает готовые значения, не вычисляет индекс/эффект/пороги.

## Реальная анкета main → SurveyPeriod

`app/ml_mapping.py` сохраняет точный текст вопросов из `docs/forms.md` и исходные оценки
1–10. `program_id=ML_PROGRAM_ID`, `intern_id=pair_{db_id}`, `period` из M1…M6;
`response_id=pair_{id}_{month}_{role}`. Backend выбирает последнюю версию по прежнему
upsert `(pair_id,role,month)`. Имена, контакты, направление и received_at в ML не отправляются.
Дата приёма не является содержательным изменением; hash запроса не меняется от дубля доставки.
`q_better`/`q_barrier` остаются разными ответами, без склейки/переписывания цитат и вопросов.

Численная политика находится **только** в `ml_service/mappings/dashboard-demo.yaml`:

| Поле обеих ролей | ML фактор | Численный gap |
|---|---|---|
| f_clarity | R03, понимание роли и задач | demo-сопоставление разрешено |
| f_workload | R04, рабочая нагрузка | не сопоставляем: комфорт/адекватность не одинаковая формулировка |
| f_inclusion | R07, интеграция в коллектив | demo-сопоставление разрешено |
| f_mentor | не сопоставлен численно | составной вопрос: поддержка + feedback / совместная работа + время |
| f_motivation | не сопоставлен | интерес/инициатива не тождественны развитию R05 |
| f_future | не сопоставлен | желание/возможность остаться не равно ясности процесса R09 и не равно R10 |

Непокрытые вопросы всё равно передаются как rating: ML явно выдаёт `unmapped_rating`,
не превращает их в благополучие. Это приводит к `partial` при наличии таких оценок,
низкому покрытию и приоритету insufficient_data. Нет ни перенормировки весов, ни
баллов за «мотивацию» вне словаря, ни вывода намерения уйти из оценки будущего.
Это **demo default**, не утверждённый HR mapping. Шкала/порог mapping (1–2 high,
3–5 moderate, 6–10 none) — демонстрационные, не калиброванные на МГТС.

Произвольные комментарии не умеет понимать fixture mock. Для smoke добавлен отдельный
catalogue `dashboard_mock_extractions.json`: точные синтетические ответы с настоящими
формулировками вопросов, для месяцев 1–6. Неизвестный текст → partial/ошибка компонента,
не скрытая NLP. Основной fixture-каталог ML P0 сохранён без замены. Реальная LLM не используется.

## AnalysisResult → dashboard card

| ML | Поле dashboard | Смысл |
|---|---|---|
| risk.score | risk / base | nullable число баллов, без округления половинок |
| risk.score_band | band | только translation routine→low/elevated→watch/high→critical; null→unknown |
| risk.priority | priority | приоритет поддержки, не восстанавливается из score |
| risk.data_coverage | data_coverage | доля покрытия факторов, не response rate |
| risk.missing_required_roles | missing_required_roles | отдельно от наличия строки анкеты |
| factors[].id/name/contribution/weight/state | factors[].key/label/points/weight/state | все факторы, динамически |
| factors[].evidence | factors[].evidence | принятие/review/rejection и ссылки на правила сохранены |
| принятая text quote | factors[].quote | дословная цитата стороны, не сгенерированный пересказ |
| accepted rating evidence | score_intern/score_mentor/scale_min/max | исходные значения, шкала не всегда 1–10 |
| discrepancies[].normalized_gap | factors[].gap | 0–1, без прибавки к индексу |
| discrepancy.threshold_exceeded | comparison_threshold_exceeded / has_gap | критерий ML, frontend не назначает свой |
| recommendations | steps | ID, targets, owner, критерии выполнения и подтверждения устранения |
| metadata / analysis_id | ml_metadata / ml_analysis_id | trace, версии и воспроизводимость |

`gap_penalty=text_penalty=0` оставлены как совместимые legacy поля. Они ничего не
добавляют. `reasons` — представление активных факторных вкладов, не отдельные баллы.
Полный ML JSON хранится в `ml_runs` и `ml_results.analysis_json`; оригиналы — по прежнему
в `submissions`. Индивидуальные reductions действий могут пересекаться и не суммируются.

## Сценарий и история

Backend вызывает `/v1/scenario` по сохранённому analysis_id и ID доступных мероприятий.
`POST /api/pairs/{id}/scenario?month=M3` принимает `{action_ids:[...]}` и возвращает
ScenarioResult. Клиент не передаёт score/веса/targets. Выбор A01+A11 устраняет уникальный
R01 один раз: 17→5. Все действия, включая A03, условно устраняют также R03: 17→0.
Это условие полного подтверждённого устранения, не прогноз эффекта. Текущий score и
immutable `ml_runs` не меняются. При потере ML snapshot сценарий недоступен, но сохранённый
фактический анализ backend остаётся читаемым.

История — сохранённые observed scores по конкретной паре/месяцу. Пропуск — null,
а не 0 и не продолжение прошлой проблемы. `temporal_status=not_implemented`, delta=null,
прогноз не рисуется. Сопоставимая динамика с учётом версий/coverage остаётся отдельной ML
задачей; backend не заменяет её линейным прогнозом. Групповой avg — среднее доступных
наблюдаемых индексов текущего месяца, не прогноз/вероятность; полнота видна отдельно.

## Состояния, cache, исправления

`pending`: анкеты сохранены, расчёт ждёт; `ready`: обработка завершена, coverage может быть
неполным; `partial`: сбой компонента; `insufficient_data`: нет meaningful observations;
`error`: ML недоступен/ответ невалиден; `missing`: нет анкет за период.
Ни error, ни pending/missing не заменяются 0 или fixture. Среднее исключает null.

GET карточки/списка/месяца не вызывает ML. Cache ключ: нормализованный вход,
версии knowledge/mapping в нём, URL сервиса и версия adapter. При изменении содержания
анкеты старый результат скрывается как pending до нового пересчёта. Перед публикацией
ответа проверяется hash актуальных анкет. Error можно повторить через recompute;
неизменённый partial сохраняется до исправления ввода/смены версии. Для повторной обработки
того же partial после замены provider пока нужен отдельный будущий force/retry контракт.
Смена содержимого KB/mapping требует новой версии; изменение файла под тем же номером
не является допустимой инвалидацией cache. Локальные thread locks coalesce пересчёты;
несколько процессов backend без внешней очереди пока не поддерживаются.

MLClient проверяет принадлежность ответа паре/периоду/версиям, вложенные поля, конечность
чисел, уникальность факторов и совпадение суммы вкладов со score. Это проверка целостности
контракта, не второй скоринг. Неполный вложенный JSON не сохраняется как ready.
До POST выполняется health-проверка `provider=mock,data_mode=demo`; DeepSeek намеренно
не допускается первой интеграцией. Это локальный prototype, не замена auth/tenant isolation.
