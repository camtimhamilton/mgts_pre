# Оптимальный путь интеграции ML-сервиса (ветка `ml`)

Документ — решение, а не вариант. Всё, что ниже, можно реализовать, проверить и откатить.
Коротко: **их движок считает базовый индекс, наш остаётся продуктом; переключение — флагом,
по умолчанию выключено, решение включать принимается на финале по реальным данным.**

---

## 1. Резюме

| Вопрос | Ответ |
|---|---|
| Интегрируем? | Да, как sidecar-сервис и второй контур расчёта |
| Кто главный индекс? | Наш, пока ML не доказал покрытие на реальных данных |
| Когда включаем? | Флагом `ML_MODE=sidecar`; на финале — только после проверки маппинга |
| Сколько работы | 2.5–3.5 дня; при сроке меньше 4 дней — только фаза 0 |
| Что не делаем | Не мержим ветки, не показываем два индекса одновременно, не меняем их базу знаний |

Главный риск не в коде. Реальные анкеты МГТС мы увидим только на финале, и их вопросы могут
покрыть лишь часть из десяти факторов R01–R10. Если покрытие ниже 0.6, их модель честно
вернёт `insufficient_data` — и как основной индекс она бесполезна. Поэтому включение —
**решение по факту данных**, а не заранее.

---

## 2. Почему именно так: четыре варианта

| Вариант | Ценность | Риск | Время |
|---|---|---|---|
| A. Полностью заменить наш расчёт их движком | высокая методологически | высокий: другой UI, пороги, история, реальный текст | 5–7 дней |
| B. Два индекса на экране | сомнительная: путает жюри | средний | 2 дня |
| C. **Гибрид: их база + наш текст и продукт, флаг** | высокая, обратимая | низкий | 2.5–3.5 дня |
| D. Только идеи, без сервиса | низкая | нет | 1–2 часа |

Выбран **C**. Причины:

- их сильная часть — числовая методология: 10 факторов, веса, severity, coverage, конфликты;
- наша сильная часть — продукт: приём, импорт, история, интерфейс, деплой, текст с цитатами;
- их текстовый слой на реальных данных не работает (fail-closed allowlist), поэтому текст
  остаётся нашим — и это не компромисс, а разделение ответственности;
- всё переключается флагом, значит демо не может сломаться из-за ML.

## 3. Целевая архитектура

```
Яндекс Форма ──► /api/ingest ──► наш backend (мастер-система)
                                      │
                                      ├─► наш LLM: сигналы, цитаты, текстовая надбавка
                                      │
                                      └─► ML_MODE=sidecar
                                             │  POST /v1/analyze (только оценки)
                                             ▼
                                      контейнер ml (внутренняя сеть)
                                             │
                                      R01–R10, score, coverage, рекомендации
                                             ▼
                              снапшот: data_json.ml + итоговый risk
```

Правила:

- ML-контейнер не имеет публичного порта, доступен только нашему backend по `http://ml:8000`.
- Наш снапшот остаётся единственным источником истории, дельт, сценариев и рейтинга.
- Ответ ML кладём целиком в `data_json.ml` вместе с версиями KB, mapping и `analysis_id`.
- Любая ошибка ML — деградация к нашему расчёту, без падения карточки.

## 4. Что считается итоговым индексом

Их score не заменяет наш целиком — он заменяет **базу**. Разрыв перестаёт начислять баллы:
по их методологии расхождение — диагностический сигнал, а не добавка. Это снимает двойной счёт
(низкая оценка одной стороны уже повышает severity).

```
base  = ml.risk.score            # 0…80 при покрытии 9 из 10 факторов (R10 только текст)
text  = min(12, Σ весов сигналов) # наши сигналы left_intent/burnout/offer_doubt/conflict
risk  = round(clamp(base + text, 0, 100))

gap   = ml.discrepancies          # показываем, но в risk не добавляем
```

Почему 80, а не 100: R10 (прямое намерение уйти) весит 20 и по их правилам не начисляется
баллами — только флаг. У нас этот смысл закрывает текстовый сигнал `left_intent` (максимум 12),
который и добавляется к базе.

Пороги полос оставляем наши — 35 / 60. Их 20 / 40 переключили бы весь демо-набор в красную
зону и потребовали бы переверстать экран; менять пороги вместе с индексом — двойное изменение.
Решение фиксируем в документации: «полосы 35/60 — продуктовые, score — экспертный».

Сценарии: наш график и наша модель затухания, но `reduction` берём из их рекомендаций
(`potential_reduction`), с общим потолком 25 — как сейчас.

## 5. Маппинг: анкета → факторы

Их модель требует `question_id` + `role` + шкалу + таблицу уровней. Наши шесть факторов
покрывают 57 весов из 100 — ниже порога 0.6. Поэтому добавляем три вопроса; их можно
задать в форме, которую мы создаём сами.

| Наш вопрос (payload) | question_id | Фактор | Вес |
|---|---|---|---|
| `f_mentor` — поддержка наставника | `q_mentor` | R01 | 12 |
| `f_feedback` — **новый**: понятна ли оценка результатов | `q_feedback` | R02 | 8 |
| `f_clarity` — понятность задач | `q_clarity` | R03 | 10 |
| `f_workload` — комфорт нагрузки | `q_workload` | R04 | 8 |
| `f_motivation` — интерес и рост | `q_motivation` | R05 | 10 |
| `f_expectations` — **новый**: совпадение с ожиданиями | `q_expectations` | R06 | 8 |
| `f_inclusion` — включённость в команду | `q_inclusion` | R07 | 7 |
| `f_resources` — **новый**: доступы и инструменты | `q_resources` | R08 | 7 |
| `f_future` — уверенность в будущем | `q_future` | R09 | 10 |
| открытый текст | — | R10 | 20 |

Итого покрытие: 80 / 100 = **0.8** при пороге 0.6 — модель работает в штатном режиме,
R10 остаётся неизвестным и закрывается нашим текстовым сигналом.

Шкала 1–10, где 10 — хорошо. Таблица уровней (severity):

```yaml
levels: {1: high, 2: high, 3: high, 4: moderate, 5: moderate, 6: moderate,
         7: none, 8: none, 9: none, 10: none}
```

Файл `mappings/mgts-v1.yaml` — 9 вопросов × 2 роли = 18 rating-записей плюс две text-записи
на будущее. Пример записи:

```yaml
version: mgts-v1
entries:
  - role: intern
    question_id: q_clarity
    type: rating
    factor_id: R03
    comparison_key: role_clarity
    direction: higher_is_better
    scale_min: 1
    scale_max: 10
    levels: {1: high, 2: high, 3: high, 4: moderate, 5: moderate, 6: moderate,
             7: none, 8: none, 9: none, 10: none}
```

Запрос к ML (только оценки, без текста — так обходим их allowlist):

```json
{
  "program_id": "mgts-2026",
  "intern_id": "pair-12",
  "period": 5,
  "mapping_version": "mgts-v1",
  "responses": [
    {"response_id": "r-intern-12-5", "respondent_role": "intern",
     "answers": [
       {"question_id": "q_clarity", "question_text": "Насколько понятны задачи",
        "type": "rating", "value": 3.0, "scale_min": 1.0, "scale_max": 10.0}
     ]},
    {"response_id": "r-mentor-12-5", "respondent_role": "mentor", "answers": [ ... ]}
  ]
}
```

Почему без текста: их mock-экстрактор знает только 20 фикстур, на незнакомом тексте
возвращает `partial` и игнорирует текст. Мы всё равно шлём только оценки — получаем
`completed` и детерминированный числовой результат. Наш текст живёт отдельно.

## 6. Что берём из ответа ML и куда кладём

| Поле ML | Куда в карточке |
|---|---|
| `risk.score` | база индекса |
| `risk.data_coverage` | бейдж «данные: 80%» |
| `risk.priority` | статус: `insufficient_data` → «мало данных» |
| `factors[].contribution > 0` | причины (топ-3), с русскими названиями из `factors.yaml` |
| `factors[].state == conflicting` | бейдж «стороны расходятся» |
| `discrepancies[]` | блок разрыва (вместо нашего расчёта разрыва) |
| `recommendations[]` | шаги: `potential_reduction` → reduction, `responsible` → owner |
| `warnings[]` | бейдж «требует проверки» |
| `analysis_id`, `metadata` | в `data_json.ml` для воспроизводимости |

Если `score` is `null` или сервис недоступен — работает наш расчёт, в карточке плашка
«экспертный слой недоступен».

## 8. Этапы

### Фаза 0. Идеи без сервиса — 2–3 часа

Делается в нашем коде, не зависит от ML, улучшает продукт сразу.

- Показывать покрытие данных: сколько из шести факторов наблюдено у пары.
- Статус «недостаточно данных» вместо «низкий риск», если наблюдено меньше половины.
- Состояние «стороны расходятся» для факторов с разрывом ≥ 4 (сейчас есть только бейдж разрыва).
- Прямое «хочу уйти» — отдельная плашка «требует разговора»; баллы оставляем, но фраза меняется.
- Не ставить в топ списка пары с покрытием ниже порога.

**Готово, когда:** тесты зелёные, на мок-наборе видно покрытие и статусы, индекс не изменился.

### Фаза 1. Сервис в контейнере — 0.5 дня

- `git subtree add --prefix services/ml origin/ml` (история сохраняется).
- Dockerfile: python 3.12-slim, зависимости из `pyproject.toml`, `uvicorn app.main:create_app --factory`.
- В compose: сервис `ml`, без `ports`, healthcheck на `/health`, `restart: unless-stopped`.
- Проверка: `docker compose exec pulse curl http://ml:8000/health` отвечает.

**Готово, когда:** контейнер поднимается вместе со стеком и отвечает на `/health`.

### Фаза 2. Адаптер и расчёт — 1 день

- `app/ml_client.py`: `analyze(payload, pair_id, period) -> MLAnalysis | None`.
- Маппинг payload → `SurveyPeriod`, версия `mgts-v1`, только rating-ответы.
- Разбор ответа в наш формат: `base`, `coverage`, `priority`, `factors`, `recommendations`, `discrepancies`.
- Формула `risk = clamp(base + text, 0, 100)`; gap не в баллах.
- Флаг `ML_MODE=off` по умолчанию: код не вызывается, поведение бит-в-бит как сейчас.
- Тесты на записанном ответе (`tests/fixtures/ml_analyze_response.json`), без живого сервиса.

**Готово, когда:** при `off` все текущие тесты зелёные; при `sidecar` карточка строится,
таймаут ML даёт деградацию, а не 500.

### Фаза 3. Интерфейс — 0.5 дня

- Русские названия R01–R10 в причинах (из их `factors.yaml`).
- Бейдж «данные: 80%»; при `insufficient_data` — «мало данных».
- `conflicting` — отдельный бейдж, без усреднения.
- Плашка «экспертный слой недоступен» при деградации.
- Переключатель режима не в UI, только `.env`.

### Фаза 4. Проверка и репетиция — 0.5 дня

- Прогон мок-набора 60 ответов в двух режимах, сравнение карточек.
- Замер: сколько занимает вызов ML на пару-месяц (цель < 300 мс на ratings-only).
- Проверка, что при выключенном ML демо выглядит и работает как раньше.
- Обновление [docs/api.md](api.md) и [docs/spec.md](spec.md).

### Фаза 5. Решение на финале — 10 минут

После загрузки реальных анкет:

1. Сопоставить их вопросы с нашими 9 ключами в импорте.
2. Посчитать покрытие: сколько весов закрыто.
3. Если ≥ 0.6 — включить `ML_MODE=sidecar`, пересчитать, проверить две карточки.
4. Если меньше — оставить `off`, показать продукт на нашем индексе.

Это заранее прописанный переключатель, а не импровизация.

## 9. Временной план относительно финала

| Дней до финала | Что делаем |
|---|---|
| ≥ 6 | Фазы 0–4 полностью, затем репетиция |
| 4–5 | Фазы 0–3, фазу 4 совмещаем с общей репетицией |
| 2–3 | Только фаза 0 + сервис в контейнере без включения (фаза 1) |
| ≤ 1 | Только фаза 0, если она не трогает критический путь; иначе ничего |

Красная линия: **за сутки до финала не меняем расчёт и не включаем ML в демо-путь**.

## 10. Риски и что с ними делаем

| Риск | Вероятность | Снижение |
|---|---|---|
| Реальные вопросы не покрывают R01–R09 | высокая | гейт на финале, `ML_MODE=off`, продукт работает |
| Их сервис падает/тормозит | средняя | таймаут 3 с, деградация к нашему расчёту |
| Двойной счёт разрыва | средняя | gap не входит в risk в ML-режиме |
| Ошибка маппинга уровней | средняя | golden-тест: 10 баллов → 0, 1 балл → вес |
| Юридический вопрос по данным | средняя | текст не отправляем, только числа; решение за МГТС |
| Два контейнера усложняют деплой | низкая | `depends_on` + healthcheck, деплой одной командой |
| Соблазн включить на сцене «по-быстрому» | высокая | флаг и гейт в чек-листе финала |

## 11. Откат

- `ML_MODE=off` в `.env`, `docker compose up -d` — всё как раньше, без пересборки образа.
- Снапшоты с `data_json.ml` остаются читаемыми: старые карточки не ломаются.
- Если ML-контейнер не нужен — убрать `depends_on` и сервис из compose; код адаптера
  остаётся, но не вызывается.
- Ветка интеграции отдельная, `main` не трогаем до полной проверки.

---

## 12. Проверки, которые обязаны быть зелёными

- `ML_MODE=off`: 120 текущих тестов + новые тесты адаптера (он не вызывается).
- `ML_MODE=sidecar`: карточка на записанном ответе; маппинг 1→high, 10→none; coverage 0.8.
- Таймаут: ML не ответил за 3 с → карточка на нашем расчёте, плашка деградации.
- Контракт: payload проходит их схему (проверяем их же валидатором в тесте).
- Отсутствие сети: при `off` ни одного исходящего запроса к ML (проверка счётчиком).
- Сквозной: форма → ingest → ML → снапшот → карточка < 30 с.

## 13. Что попросить у автора ветки

1. Dockerfile или разрешение положить свой (нам достаточно `pip install .`).
2. Выбор mapping через env (`MGTS_MAPPING`) — либо согласие на этот патч.
3. Русские названия факторов — если их нет в `factors.yaml`.
4. Ответ по реальным данным: разрешены ли они и в каком режиме.
5. Подтверждение, что ratings-only — штатный режим, а не побочный эффект.

---

## 14. Что не делаем

- Не мержим `ml` в `main`: независимые истории, общий пакет `app/`.
- Не показываем два индекса одновременно.
- Не правим их базу знаний, веса и пороги под наш демо-набор.
- Не отправляем реальные комментарии во внешнюю модель без решения МГТС.
- Не включаем ML в критический путь финала до проверки покрытия.
